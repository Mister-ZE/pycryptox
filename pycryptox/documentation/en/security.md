# Security

This document describes Pycryptox's threat model, its guarantees, and its known limits.


## What Pycryptox guarantees

**Confidentiality of data at rest**: encrypted bundles and Keyx are unreadable without the corresponding key or password. Confidentiality relies on ML-KEM-512 (for BLUE, RED, BLACK) and Argon2id + ChaCha20-Poly1305 (for PURPLE and the Keyx).

**Integrity and authenticity**: ChaCha20-Poly1305 is an AEAD (Authenticated Encryption with Associated Data) scheme. Any modification of a bundle or a Keyx file is detected at decryption. An attacker cannot alter a ciphertext without being detected.

**Post-quantum resistance**: asymmetric operations (BLUE, RED) use ML-KEM-512, standardized by NIST under FIPS 203, designed to resist quantum-computer attacks (Shor's algorithm). PURPLE, being purely symmetric (Argon2id + ChaCha20-Poly1305), is also resistant to known quantum attacks (Grover's algorithm halves the effective security of a symmetric scheme, but 128 bits remain largely sufficient).

**Side-channel resistance (ML-KEM)**: ML-KEM-512 operations are executed via liboqs, a C implementation compiled with constant-time optimizations. This protects against timing analysis attacks, where an adversary measures operation execution times to deduce information about the keys.


## What Pycryptox does not guarantee

### Memory zeroization

In Python, `bytes` and `str` objects are immutable. Once a private key or plaintext message exists in memory, it cannot be reliably overwritten. Python's garbage collector may copy or move data in memory without the program controlling it.

Pycryptox performs symbolic destruction (`variable = b'\x00' * len(variable)` + `del variable` + `gc.collect()`) on critical paths (BLUE, RED), but this does not guarantee that the original data is erased from physical memory.

For a zeroization guarantee, a hardware module with attested memory would be required. This is one of the goals of the Cryptbox project — a hardware module companion to Pycryptox, currently in the design phase, that would provide an isolated execution environment where keys are generated, used, and destroyed with hardware attestation. Cryptbox is not yet available.

### Independent audit

Pycryptox has not undergone any formal third-party security audit. The code has been written carefully and tested extensively, but it has not been validated by a professional auditor. For very high-criticality deployments, an audit is recommended before production use.

### Protection against an adversary with root access

If the attacker has administrator (root) access to the machine on which Pycryptox runs, they can read the Python process memory (and see keys in plaintext), intercept keystrokes to capture passwords, or modify the Pycryptox code itself.

Pycryptox protects data at rest and in transit, not data being processed on a compromised machine.

### Forward secrecy

Pycryptox does not implement forward secrecy. If a user's ML-KEM-512 private key is compromised, all past bundles encrypted with the corresponding public key are decryptable. Pycryptox is designed for at-rest encryption, not for interactive communication sessions like TLS.


## Protocol-specific limits

### PURPLE

**Offline brute-force**: an attacker who captures a file encrypted with PURPLE can attempt to brute-force it by testing passwords. Argon2id slows down each attempt (~50 ms), but an attacker with specialized hardware (FPGA, ASIC) can parallelize. The passphrase generated by `genkeys` has ~77.5 bits of entropy, which is robust against online brute-force but may be insufficient against a state-level attacker with massive resources. For high-security scenarios, use a longer passphrase (8+ words).

### BLUE

**Conditional deniability**: BLUE's deniability is cryptographic (the bundle does not betray the existence of two channels — see the dedicated section in the [BLUE](blue.md) documentation), but it depends on user behavior. If both private keys are stored in the same place, deniability is null. Physical key separation is required.

**Decoy credibility (operational)**: BLUE makes the two channels cryptographically indistinguishable, but it cannot ensure the decoy content is *credible*. An empty or absurd y-channel message defeats the deniability regardless of what the cryptography does. The credibility of the decoy is the responsibility of the application layer.

**Maximum size**: in v2.0, BLUE caps each slot at **1 GiB** with 8 fixed padding buckets (4 KB, 16 KB, 64 KB, 256 KB, 1 MB, 16 MB, 256 MB, 1 GiB). At sizes approaching the cap, peak RAM usage may reach ~7–9 GiB; users on memory-constrained machines should stay well below. In v1.0 (legacy, frozen), the cap is 1 MB.

**Legacy oracle on v1.0**: v1.0 bundles include an unauthenticated noise layer between the authenticated chemkey blobs. An attacker who can submit modified v1.0 bundles and observe success/failure can map the chemkey positions, partially compromising slot identification. v2.0 removes the noise layer entirely (the bundle is `[order_flag][len][enc_x][enc_y]`, both AEAD-authenticated), eliminating this oracle. New deployments should use v2.0.

### RED

**Trusted dealer**: in v1.0, the entity that calls `genkeys()` sees the complete private key before splitting it into shares. This entity must be trusted.

**Static shares**: RED shares are usable indefinitely. There is no revocation mechanism. If a share is compromised, a new key set must be regenerated and new shares redistributed.

**Share identifiability**: each share contains an index (1 to n) in plaintext. An attacker who captures a share knows it is a secret-sharing share and knows its number. To protect this information, shares can be individually encrypted with PURPLE before distribution.


## Dependencies and attack surface

| Dependency | Role | Risk |
|---|---|---|
| `liboqs` (C) | ML-KEM-512 | C implementation, maintained by the Open Quantum Safe project (Linux Foundation). Constant-time. Not yet FIPS 140-3 certified (process underway). |
| `cryptography` (Python/C) | ChaCha20-Poly1305 | Python bindings for OpenSSL/BoringSSL. Widely audited. |
| `argon2-cffi` (Python/C) | Argon2id | Python bindings for the Argon2 reference C implementation. Winner of the Password Hashing Competition (2015). |
| `rapidfuzz` (Python/C) | Fuzzy search | Used only for Keyx search. No impact on cryptographic security. |


## Recommendations

1. **Use strong passphrases** for PURPLE and the Keyx. The passphrase generated by `crx.purple.genkeys("1")` is an acceptable minimum.

2. **Physically separate BLUE keys** by using the `keys` (on the machine) and `ckeys` (on external media) Keyx. In a non-deniability scenario, only the `keys` Keyx is used; the `ckeys` Keyx is not created.

3. **Distribute RED shares through separate channels**. Do not send all shares to the same place. Each participant must store their share independently.

4. **Do not expose decryption results** to unauthenticated third parties, particularly for BLUE.

5. **Keep Pycryptox up to date**. Post-quantum algorithms are an active research area. Pycryptox updates incorporate the latest versions of liboqs and fix any vulnerabilities.
